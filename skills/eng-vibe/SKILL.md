# 工程级 Vibe Coding 工作流(Engineering-Grade Vibe Coding)

核心原则:**工程级 vibe coding 不是让 AI 写出更好的代码,而是搭一个让它写不出坏代码的环境。人负责判断和验收,机器负责生成和守门。**

凡是靠"记得"来维持的约定都会被破坏,凡是靠测试/脚本/CI 守住的约定才真正存在。执行本 skill 时,每一步都要问:**"违反这条规矩时,什么东西会红?"** 答不上来,这条规矩就不存在。

## 何时用哪个入口

- 新项目从零开始 → 从第 1 步走全流程
- 已有项目加功能 → 从第 3 步进入,但先检查第 1、2 步的产物是否存在(没有宪法的老项目,先补一份最小宪法再动手)
- 用户问"能不能发布/交付了" → 直接跳第 6 步,跑交付清单

## 第 1 步:先写宪法,再写代码

动手写任何代码之前,和用户一起产出项目根目录的 `CLAUDE.md`(模板见 [references/constitution-template.md](references/constitution-template.md))。必须包含三块:

1. **业务红线**:什么绝对不能做(合规、资损、隐私)。这类约束 AI 自己推不出来,必须由人显式声明。逐条向用户提问确认,不要替用户假设
2. **技术硬约定**:数据流路径(谁能读写什么)、并发/幂等模式、常量唯一源在哪、错误处理策略(fail-open 还是 fail-close,逐场景定)
3. **产品路线**:已拍板的方向和明确不做的事,防止后续会话重新发明产品

宪法写完读给用户确认。这份文档是每次会话的记忆假体,它的质量决定后面所有代码的质量上限。

写法要求(详见模板头部的三条检验标准):每条**具体到可判对错**——"函数不超过 30 行"成立,"代码要简洁"不成立;**短即高信号**——代码里能看出来的不写,删掉后 AI 行为不变的条款删掉。CLAUDE.md 对模型只是参考上下文而非最高指令,模糊冗长的条款会被直接忽略——这和守护测试是同一个道理:说不清"违反它时什么会红"的条款等于不存在。

## 第 2 步:约定必须机器可执行

宪法里每一条技术约定,落成一个会红的东西,三选一:

- **守护测试**(guard test):扫描源码断言约定成立。典型:状态/枚举常量必须引用唯一源,禁止裸字面量——测试里 grep 源码,发现字面量直接 fail 并打印文件行号
- **脚本**:需要跨目录同步/生成的东西写成脚本(如共享代码分发),并在守护测试里校验副本与母本一致
- **Lint/CI 规则**:格式、依赖版本锁定、禁止 import 的路径

优先级:先把**最贵的约定**(违反后返工成本最高的:状态机、权限边界、幂等键)守住,再逐步覆盖。每写一条守护,故意违反一次,亲眼看到它红,才算完成。

守护测试就位后,把它接入自动闸门:在项目根目录建 `eng-vibe.config.json` 写入 `{"guardCommand": "<快速守护命令>"}`(或在 package.json scripts 里定义 `guard`)。若本 skill 以 plugin 形式安装,首次编辑时守护 hook 会拦截并显示授权命令——出于安全,hook 不自动执行未信任项目的命令;把 `--trust` 命令转给用户**人工**执行一次即完成接入(用户不想启用则 `--untrust` 静默跳过),之后每次文件编辑自动执行守护命令,红了立刻拦截。守护命令只跑约定扫描类测试,须在几秒内完成。

## 第 3 步:小步迭代,每步闭环

- 一次会话/一次任务只做一个 issue 大小的事。大需求先拆成 issue 列表,和用户确认优先级
- 动手前先复述:用 2-5 句话向用户复述理解的需求、方案、影响面(改哪些文件、动不动状态机、要不要新守护测试),确认后再写代码。纠偏成本在方案阶段是 1,在代码阶段是 10
- 每个 issue 完成后立即执行第 4 步验收,通过才进入下一个
- 验收通过后顺手问一句:这次踩的坑有没有值得写进宪法的?宪法里有没有已经失效的条款?宪法跟着代码演进——过时条款会让整份文档失去信用,连带正确的条款一起被无视
- 提交信息带 issue 号和一句话结论(如 `issue #12: 抢单并发改条件原子更新`),git 历史即工作日志,是未来会话最廉价的上下文

## 第 4 步:完成的标准是证据,不是"我做完了"

宣布任何任务完成之前,必须出示验证证据,且证据要贴在回复里:

- 改了逻辑 → 跑测试,贴测试输出(包括守护测试)
- 改了接口 → 真实调用一次,贴请求/响应
- 改了 UI → 真机/浏览器跑一遍,描述或截图关键路径
- 修了 bug → 先写复现(失败的测试),再修,贴修复后由红转绿的输出

没有验证的功能等于不存在。如果环境跑不了验证(缺凭据、缺设备),明确告诉用户"此项未验证,需要你在 X 环境执行 Y 确认",不要默认它是好的。

## 第 5 步:生成和审查分离

功能完成后,用**独立的子代理**做对抗审查,审查者的任务是找茬而不是确认。若本 skill 以 plugin 形式安装,直接调用 `eng-vibe-reviewer` 子代理;否则按 [references/review-checklist.md](references/review-checklist.md) 新开会话切换审查角色。至少覆盖:

- 权限与数据泄露:每个数据出口是否按角色脱敏?新字段默认可见还是默认不可见?(正确答案:白名单模式,默认不可见)
- 并发与幂等:同一操作被并发/重放两次会怎样?
- 时区、边界值、失败路径:接口超时/第三方挂了走哪个分支?
- 与宪法逐条对照:有没有违反业务红线的功能被"顺手"做出来?

审查发现的问题回到第 3 步处理。审查通过的标准同样是证据:审查者列出检查了哪些项、各项结论。

## 第 6 步:交付的是包,不是代码

对外说"可以发布了"之前,跑一遍 [references/ship-checklist.md](references/ship-checklist.md)。交付包五件套,缺一项都还是 demo:

1. 能跑的代码(含从零部署到能跑的完整步骤)
2. 测试(业务测试 + 守护测试,CI 里全绿)
3. 部署文档(要改哪些配置项、控制台要点哪些开关,精确到字段名)
4. 已知问题清单(issue 列表,含"明确不修"的和理由)
5. 运维路径(出了问题看哪里的日志、关键日志带什么关联键)

逐项给出状态(✅/❌/不适用+理由),❌ 项列出补齐方案交用户决策。
