# 项目宪法模板(CLAUDE.md)

> 复制本文件为项目根目录的 `CLAUDE.md`,逐节填写。写不出来的节先和用户讨论,不要留空也不要编造。
>
> 三条检验标准:
> 1. **陌生 AI 测试**:一个从没见过这个项目的 AI,只读这份文档,能不能避开所有致命错误?
> 2. **具体可验证**:每条能判对错——"函数不超过 30 行"成立,"代码要简洁"不成立。CLAUDE.md 对模型只是参考上下文而非最高指令,模糊条款会被直接忽略。这与守护测试同理:说不清"违反它时什么会红"的条款,写了等于没写
> 3. **短即高信号**:代码里能看出来的不写;删掉后 AI 行为不变的条款删掉。长内容(完整状态机图、部署全流程)放独立文件,正文用 `@相对路径` 引入或留索引

```markdown
# <项目名> — 开发约定(改代码前必读)

<一句话:这是什么产品,核心链路是什么。例:用户发单 → 师傅抢单 → 上门服务 → 确认评价>

## 不可破坏的业务红线

<AI 自己推不出来的约束,每条写清"为什么"。典型来源:合规、资损、隐私。例:>
1. 平台永远不代收交易款——<原因:二清合规风险>。任何"平台收款再结算"的功能都不做
2. <敏感数据> 只在 <条件> 下对 <角色> 可见
3. 界面上不出现兑现不了的承诺和没有后端的假入口

## 产品路线(已拍板,新功能设计须与此对齐)

- 现阶段做什么:<...>
- 明确不做什么(及触发条件):<...>
- 竞品参照/反面教材:<...>

## 硬性技术约定

<每条约定末尾标注它的守护物,固定格式 `【守护:测试/脚本/CI 规则的路径】`。没有守护物的约定要么补上,要么承认它只是愿望。>

- 数据流:<谁能读什么、写什么走哪条路。例:所有读写走服务端函数,前端不直连数据库;读 X 一律经 Y 接口,它负责按角色脱敏(白名单)>【守护:<test/guard.dataflow.js>】
- 并发:<状态流转用条件原子更新 where(id, 前置状态).update(...),靠影响行数=0 判败>【守护:<...>】
- 状态机:<状态列表和流转图;常量唯一源在哪个文件>【守护:<test/guard.state.js,扫描裸字面量>】
- 幂等:<关键写操作的幂等键设计。例:身份记录用 userId 作主键;账务用 requestId;评价用 orderId>【守护:<...>】
- 时区:<运行环境时区;涉及本地时间怎么换算>【守护:<...>】
- 错误处理:<哪些场景 fail-open、哪些 fail-close,逐场景写>【守护:<...>】

## 共享代码规则(防复制漂移)

- <常量/枚举的唯一源文件路径>
- <如有跨目录副本:同步脚本是什么,改了母本必须跑什么命令>

## 常见改动怎么做

<把 3-5 个最高频的改动写成菜谱:加一个 X 需要动哪几个文件、跑什么脚本、重新部署什么。这是防漂移最有效的一节。>

## 部署备忘

- 必改的配置项:<文件路径 + 字段名>
- 外部控制台要做的事:<逐条>
- 完整流程见 README.md;待办见 <issue 跟踪处>
```

## 项目变大后怎么组织(给宪法作者的指引,不进宪法正文)

- 根 CLAUDE.md 超过 ~100 行时拆分:正文只留业务红线和索引,其余按主题放 `.claude/rules/*.md`(Claude Code 自动加载,支持子目录),或用 `@.claude/rules/xxx.md` 语法显式引入
- 子目录差异化约定放该目录自己的 CLAUDE.md(如 `frontend/CLAUDE.md` 写"组件用函数组件");离工作目录越近的文件优先级越高
- 个人本地配置(本机端口、密钥文件路径)放 `CLAUDE.local.md` 并加入 .gitignore,不进版本控制
- 团队成员的个人偏好(回复语言、代码风格口味)放各自的 `~/.claude/CLAUDE.md`,不要混进项目宪法
