# 交付清单(第 6 步用)

> 对外说"可以发布"之前逐项打勾。每项给状态:✅ / ❌(附补齐方案) / 不适用(附理由)。缺 ❌ 项时结论只能是"还是 demo"。

## 1. 能跑的代码

- [ ] 一台干净机器,照 README 从零走到跑起来,不需要口头补充步骤
- [ ] 所有配置项集中且有说明,没有散落在代码里的硬编码环境值
- [ ] 依赖版本锁定(lockfile 提交)

## 2. 测试

- [ ] 业务测试覆盖核心链路(至少:主流程 happy path + 每个状态流转的失败分支)
- [ ] 守护测试全部存在且通过(常量唯一源、共享副本一致性等)
- [ ] CI 配置好,主分支全绿;本地一条命令能跑全部测试

## 3. 部署文档

- [ ] 必改配置清单,精确到文件路径 + 字段名
- [ ] 外部系统要做的事逐条列出(控制台开关、回调地址、白名单、定时触发器)
- [ ] 有回滚方案:上一版怎么退回去

## 4. 已知问题清单

- [ ] 所有已知缺陷在 issue 跟踪里,不在某个人的脑子里
- [ ] "明确不修"的项写了理由
- [ ] 安全相关的已知限制向用户明示过

## 5. 运维路径

- [ ] 出了问题第一眼看哪里(日志入口、监控面板)写在文档里
- [ ] 关键日志结构化,带关联键(如 orderId/requestId),能从一条用户投诉追到全链路
- [ ] 最常见的三种故障(第三方挂了、数据不一致、任务超时)各有排查步骤
